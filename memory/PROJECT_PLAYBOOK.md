# PROJECT PLAYBOOK

## validated
- 결정론적 수집·정리·점수·중복·게시 작업은 코드로 처리한다.
- 의미 해석이 필요한 소수 항목만 현재 Claude Code 세션과 서브에이전트가 판정한다.
- QA는 운영과 동일한 진입점과 코드 경로를 사용한다.
- 운영 이력은 원자적으로 갱신하고 QA에서는 수정하지 않는다.

## candidate
- 초기 HN 필터 표현과 공급 검색 동의어는 실제 측정 및 QA 후 validated로 승격한다.
- **`CAPABILITY_STAGNATION`/`RECOVERY_REQUIRED` 상태 전이 조건은 원본 설계서에 이름만
  있고 트리거 조건이 명시되어 있지 않아, 2026-08-11 감사 배치에서 다음과 같이 해석해
  구현했다(추후 반례가 나오면 재검토할 것):
  - `CAPABILITY_STAGNATION`: 제목 생성 라운드가 전부 소진되거나 기회 풀이 비었는데
    **그 시점까지 승인된 제목이 0개**인 경우(=이 실행의 현재 데이터/방식으로는 아무것도
    못 만든다는 신호). 일부라도 진행됐으면(0개가 아니면) 그대로 `RETRYING` 유지.
  - `RECOVERY_REQUIRED`: 운영 이력(`output/history/words.txt`) 원자적 쓰기 직후
    증가분을 재검증했는데 기대한 제목과 실제로 파일에 쓰인 내용이 다른 경우 — 자동
    재시도가 안전하지 않은(중복 append 위험) 상황이라 사람 확인 없이는 다음 단계로
    진행하지 않는다.
  - 둘 다 기존 `RetryRequired`(`CAPABILITY_STAGNATION`) 또는 신규
    `RecoveryRequired`(`RECOVERY_REQUIRED`) 예외로 표현되며, `run.py` 종료 코드는
    각각 4, 5. 상세는 `src/saas_words_two/pipeline.py`의 두 예외 클래스 docstring 참고.

## candidate (구현 패턴, 재사용 시 참고)
- 새 데이터원을 추가할 때 기존 `hn_items` 같은 정규화 테이블을 그대로 재사용하고
  `source` 컬럼만 추가하면, 필터·군집·점수 등 나머지 파이프라인 코드를 전혀 고치지
  않아도 된다(GH Archive 추가 시 검증됨, `gh_archive_client.normalize_event`가
  `hn_client.normalize_item`과 동일한 dict 모양을 만드는 것이 핵심). id 값 범위가
  서로 겹치지 않는지는 반드시 먼저 확인할 것.
- 시간/날짜 문자열을 정렬 키로 쓰는 코드(선행 0 없는 `"YYYY-MM-DD-H"` 같은 포맷)는
  절대 문자열 비교하지 말고 반드시 실제 날짜/시간 타입으로 변환해 비교할 것 —
  `"...-9"` > `"...-10"`처럼 사전식 비교가 틀린다. GH Archive 커서 구현에서 실제로
  이 버그가 났고 회귀 테스트로 고정함.
- 외부 API가 UTC 리소스명을 쓰는데 파이프라인 `now`는 KST로 흐르는 구조이므로, 새
  데이터원을 붙일 때마다 시간대 변환 필요 여부를 먼저 확인할 것.
- 새 데이터원의 원본 id가 작은 정수라 기존 소스와 겹칠 위험이 있으면(Stack Exchange의
  사이트별 Post Id가 그랬음 — HN id와 같은 자릿수대), "값 범위가 우연히 안 겹친다"에
  기대지 말고 접두어를 붙여 명시적으로 재매핑할 것(`stack_exchange_client.make_item_id`:
  `9` + 사이트 코드 3자리 + Post Id 8자리 zero-pad). GH Archive는 원본 id 자체가
  이미 커서 재매핑 없이도 안전했지만, 그건 우연이지 원칙이 아니다.
- 표준 라이브러리로 못 푸는 파싱(예: 7z)이 필요한 데이터원은 CLAUDE.md §8에 따라
  라이선스·유지보수 근거를 `pyproject.toml` 주석과 `docs/policies/04`에 남긴 뒤
  추가할 것(py7zr, LGPL-2.1+, 이 배치에서 실제로 이렇게 처리함).

## 확인된 한계 (validated로 승격하지 않되, 재실험 전에 반드시 참고할 것)
- HN 검색 수집량을 늘리는 것만으로는(`search_hits_per_pattern` 40→1000, 후보
  332→4,133개) 독립 사용자 5명 이상이 동일한 구체적 문제를 언급하는 군집을
  얻지 못했다. 볼륨을 늘릴수록 서로 다른 주제만 늘어났다. 상세 근거와 실제
  검토한 군집 목록은 `memory/ACTIVE_ISSUES.md`의 DEMAND-001 참고.
- **데이터원을 다양화하는 것(2차 소스 추가)만으로도 위 한계는 해결되지 않는다.**
  GH Archive를 추가해 후보 문장을 4,133→~5,200개로 늘렸지만(실제 네트워크 수집,
  36시간치, 실제 `run.py --mode qa` 전체 실행으로 검증) `independent_user_count>=5`
  군집 19개를 전부 직접 읽은 결과 전부 보일러플레이트/템플릿이었다(GitHub 기본
  이슈 템플릿 문구가 서로 무관한 저장소 수십 개에 붙는 등, HN 관용구보다 더 심한
  새로운 오염원까지 추가됨). 근본 원인은 데이터 부족이 아니라 1차 문자열 유사도
  군집화 자체의 재현율 한계(표현이 다른 같은 문제는 애초에 못 묶음)이므로, 소스를
  더 늘려도 같은 실패가 반복될 것으로 예상됨. 상세: `ACTIVE_ISSUES.md`
  `DEMAND-001` "A안 실데이터 검증 결과".
- 결론: 검색량 증가나 소스 다양화 같은 "같은 방법을 더 크게" 실험은 이제
  반복하지 말 것 — 두 번 다 같은 실패 패턴(볼륨/소스만 늘면 보일러플레이트만
  더 늘어남)으로 확인됐다.
- **군집화 알고리즘을 TF-IDF 가중 코사인 유사도로 바꾸는 것(B안)도 해결책이
  아니다 — 오히려 기존 방식보다 false positive 군집이 더 많았다**(실측:
  같은 데이터에서 문자열 유사도 15개 vs TF-IDF 21개, 필터 적용 전 기준으로는
  19개 vs 27개). 원인: "I'd love to hear your feedback and feature requests!"
  같은 문장은 불용어 제거 후 남는 내용어가 3~7개뿐이고 그마저 거의 전부
  보일러플레이트 단어라, 어떤 가중치를 줘도(그 단어들 외엔 비교할 내용이 없으므로)
  서로 비슷하게 나온다 — TF-IDF는 "다양한 내용 중 흔한 단어를 죽이는" 데는
  효과적이지만 "내용이 애초에 거의 없는" 문장 쌍에는 효과가 없다. 짧은
  보일러플레이트 문장을 후보 추출 단계에서 사전 필터링하는 것
  (`text_filter.is_generic_courtesy_sentence`)은 어느 정도 도움이 됐지만
  (보일러플레이트 종류가 다양해서 사전 하나로는 부분적으로만 잡힘) 근본
  문제를 없애지는 못했다. `cluster_candidates_tfidf`는 코드베이스에 테스트와
  함께 남아있지만 프로덕션(`cluster_problems.py`)은 실측 결과에 따라 기존
  `cluster_candidates`를 그대로 쓴다. 상세: `ACTIVE_ISSUES.md` `DEMAND-001`
  "B안 실데이터 검증 결과".
- **결론(누적)**: 볼륨 증가, 소스 다양화, 유사도 알고리즘 교체 — 세 가지를 전부
  실측으로 시도했고 전부 근본 원인을 못 풀었다. "이 문장이 진짜 문제 설명인지
  일반적인 사교적 문구인지" 구분은 유사도 계산으로 대신할 수 없는 의미 판정이며,
  이는 애초에 `extract_and_cluster_problems`의 애매 군집 AI 판정 단계가 하도록
  설계된 일이다 — 즉 이번 세션이 19개 군집을 전부 정직하게 REJECT한 것 자체가
  설계대로 정상 동작한 결과다. 남은 방법은 판정 기준 완화(금지) 외에는 (a) 더 오래
  데이터를 쌓아 우연히 5명이 겹치는 진짜 문제를 기다리거나 (b) 근본적으로 다른
  종류의 데이터원을 찾는 것뿐이다.
